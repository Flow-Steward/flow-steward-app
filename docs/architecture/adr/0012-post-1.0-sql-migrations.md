# ADR 0012: Post-1.0 SQL Migrations on a Schema Baseline

- Status: Accepted
- Date: 2026-06-29
- Supersedes: [ADR 0011](0011-release-upgrade-path.md)

## Context

ADR 0011 established the operator database upgrade command and
kept `db/schema/*.sql` plus `db/seeds/*.json` as the canonical DB source of
truth. Its upgrade model was "idempotent compatibility steps in code" plus a
full re-apply of the canonical schema (`reconcile_canonical_schema`).

As the project approaches its first release, that model does not scale to
post-1.0 change:

- Idempotent in-code patches are hard to review, hard to order, and accumulate
  silently. They cannot express data backfills or carefully staged changes.
- Re-applying the whole canonical schema only ever adds missing objects; it can
  never express an intentional `ALTER`, index rebuild, or column migration.
- Operators had no record of *which discrete changes* a database had received,
  only a single fingerprint of the canonical snapshot.

The repository has historically forbidden a "migration chain" because, before
1.0, a second handwritten DDL source competing with `db/schema/` was pure risk.
After 1.0 the trade-off flips: the schema must be allowed to evolve, and the
safest way to do that is small, ordered, individually reviewable SQL files.

## Decision

Freeze the current schema as the **1.0 baseline** and evolve it with explicit
**SQL migrations**.

The rules are:

- `db/schema/*.sql` is the 1.0 baseline and holds the final 1.0 structure. Fresh
  installs initialize from it. There are no historical migrations:
  `db/migrations/` is empty at 1.0 and only ever receives post-1.0 changes.
- `db/migrations/` is the only allowed migration directory. A root-level
  `migrations/` directory remains forbidden.
- Post-1.0 database changes `MUST` be expressed as SQL files under
  `db/migrations/`. Per-migration Python files are not allowed.
- Migration files are named `YYYYMMDDHHMMSS_slug.sql` and applied in
  lexicographic order.
- Each file is SQL-only, carries a clear header, and declares its transaction
  mode with a marker comment: `-- transaction: true` (default) or
  `-- transaction: false` (for operations such as `CREATE INDEX CONCURRENTLY`).
  Files never contain explicit transaction-control statements; the runner owns
  transactions.
- Applied migrations are tracked in `public.platform_schema_migrations`
  (`migration_id text primary key`, `checksum text not null`,
  `applied_at timestamptz not null default now()`). There is no `applied_by`
  column: the console upgrade command has no authenticated user context.
- `flow-steward database upgrade --maintenance-confirmed --confirm` remains the
  operator-facing command. On an existing baseline with a migration ledger, it
  applies pending post-1.0 SQL migrations, refreshes canonical seeds, and
  validates the resulting canonical baseline contract before initializing the
  workflow knowledge graph, extension catalog, and checkpoint schemas. Without
  a ledger, it first verifies the existing canonical baseline schema, then lets
  the runner create the ledger and apply pending migrations. The command does
  not perform a full baseline reconcile; fresh installations initialize
  `db/schema/` separately.

## Runner Behavior

The runner lives in `core/application/tooling/db/migration_runner.py` and:

- discovers `db/migrations/*.sql`, validates filenames, and sorts them
  lexicographically;
- acquires a session-level PostgreSQL advisory lock for the whole run so
  concurrent deploys cannot apply the same migrations;
- skips already-applied migrations, and **fails with a checksum drift error** if
  an already-applied file's content has changed (edited applied migrations are
  never silently re-run);
- rejects empty or template-only migration files;
- wraps transactional migrations — including the insert into
  `platform_schema_migrations` — in a single transaction, so a mid-migration
  failure records nothing;
- runs non-transactional migrations with autocommit, first durably recording
  `in_progress:<checksum>` in `platform_schema_migrations` before executing the
  SQL, then replacing that marker with the final checksum after success;
- treats a remaining non-transactional in-progress marker as an unknown durable
  outcome and blocks automatic reruns. The operator must inspect and reconcile
  the database outcome and ledger before retrying; use
  `./flow-steward database status --json` to inspect the recorded state.

New migration files are scaffolded with
`flow-steward database generate-migration <slug>`.

## Consequences

Benefits:

- Schema change after 1.0 is explicit, ordered, reviewable, and auditable.
- Operators can see exactly which migrations a database has received.
- Fresh installs and long-lived databases converge through one command.
- Checksum tracking turns accidental edits of shipped migrations into a loud
  failure instead of silent drift.

Tradeoffs:

- There are now two DDL artifacts (the baseline and the migration files), so the
  baseline/migration boundary must be respected: 1.0 objects stay in
  `db/schema/`; post-1.0 change goes to `db/migrations/`.
- Migration authors must choose the correct transaction mode and keep files
  forward-only; downgrade is not implied (recovery is restore-from-backup).

## Alternatives Considered

- Keep ADR 0011's in-code idempotent patches.
  Rejected: not reviewable or orderable, and cannot express `ALTER`/backfill.

- Adopt a third-party migration framework (Alembic, etc.).
  Rejected: adds a dependency and a second DSL when the need is a thin,
  SQL-only, checksum-tracked runner already aligned with `db/schema/`.

- Per-migration Python modules.
  Rejected by policy: migrations must be SQL files; the runner, not each file,
  owns transactions and tracking.
