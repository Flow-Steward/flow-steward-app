# ADR 0054: Database Upgrades of Released Installations Before 1.0

- Status: Accepted (owner accepted on 2026-11-03)
- Date: 2026-11-03
- Related: [ADR 0011](0011-release-upgrade-path.md), [ADR 0012](0012-post-1.0-sql-migrations.md)
  (and its 2026-11-01 amendment on `claude/oauth-upgrade-migration`),
  [ADR 0047](0047-inbound-mcp-oauth.md)
- Changes: the parts of ADR 0012 named under "What this changes in ADR 0012"

## Context

ADR 0012 lets `db/schema/` change freely before 1.0 and reserves `db/migrations/`
for post-1.0 change. The 0.9.x line is published and installations are updated in
place, so that reading no longer holds:

- An installed database never re-reads `db/schema/`. 0.9.7 added the inbound-OAuth
  tables to the baseline only, and installations updated from 0.9.6 never got
  them. The 2026-11-01 amendment to ADR 0012 already requires a released baseline
  to change only together with an idempotent `db/migrations/` file.
- The demo installation received earlier schema changes through manual `ALTER`.
- Upcoming changes need more than DDL. The secret catalog moves existing
  credentials and must create the first approvals of the configurations it moves.
  Those approvals depend on a fingerprint computed by runtime code in Python.

What exists today in `flow-steward database upgrade` (`core/application/tooling/db/upgrade_db.py`):

- one PostgreSQL advisory lock for the run;
- refusal of a pre-release ledger (rows dated before the 2026-09-26 cutoff);
- the SQL runner of ADR 0012: checksums, drift refusal, and an in-progress marker
  for non-transactional files. Each transactional file commits on its own; the set
  of files is not one transaction;
- after SQL, fixed Python steps: observability schema, retired-schema cleanup, seed
  refresh, membership repair, workflow knowledge graph, extension catalog,
  LangGraph schema, vector health, recording the schema state.

What does not exist:

- a read-only preflight;
- a durable record of which of those steps finished;
- any check that the previous release's processes have stopped. `--maintenance-confirmed`
  is the operator's word. Maintenance mode pauses new public submissions, but
  app, worker and scheduler processes stay connected;
- a refusal by an older release to start on a database a newer release migrated.
  Only the installer path (`upgrade_db --baseline-migration-history`) checks for
  unknown applied migrations; a runtime process started by hand does not.

## Decision

### Scope and supported source

1. This ADR applies to every installation created from a published tag, from the
   0.9.x line on. A pre-release ledger remains unsupported and is refused, as today.
2. A database is a **supported source** when:
   - the recorded schema state names a baseline fingerprint this release lists as
     released. `db/released_migrations.json` keeps an append-only
     `released_baseline_fingerprints` list next to the pinned current fingerprint;
   - every applied migration is known to this release with a matching checksum,
     and the applied set is a prefix of this release's ordered files;
   - every recorded upgrade phase is known to this release.
   Skipping releases is allowed when the chain is intact. Anything else is an
   **unknown schema** and is refused before any change.

### Stages

`database upgrade` runs four stages. Stages 2–4 run under the upgrade advisory lock,
taken with `pg_try_advisory_lock`: a second concurrent upgrade fails at once with a
clear message instead of waiting.

1. **Preflight** (read-only; `database upgrade --preflight`, and always re-run at
   the start of a real upgrade under the lock). It checks the supported source, drift,
   unknown migrations and phases, the pre-release ledger, live sessions of the
   previous release, backup evidence, and every phase input file. It writes nothing
   and prints a JSON report. A blocked preflight exits non-zero, and stage 2 does
   not begin.
2. **SQL.** The ADR 0012 runner, unchanged in guarantees: each transactional file
   commits atomically with its ledger row, and a non-transactional file leaves its
   in-progress marker. The whole set is **not** one transaction, and no document may
   claim it is. A rerun applies the files that remain.
3. **Data phases.** Host-owned Python steps that run after SQL:
   - They live in one enumerated registry in `core/application/tooling/db/`. They
     are not discovered from files, and a migration cannot register or call one.
   - Each phase has a stable id, the migration ids it requires, and a declared input
     kind. It runs in one transaction that also writes its completion row to
     `public.platform_upgrade_phases`, so a phase either completed or left nothing.
   - A phase is idempotent: a rerun after completion is a no-op, and a rerun after a
     failure starts again from a clean transaction.
   - A phase never changes DDL; DDL stays in SQL files. It calls the same application
     functions as runtime. For example, the secret catalog's approval phase uses the
     runtime fingerprint function; no SQL copy of it may exist.
   - A phase reads only the database and validated phase inputs. It has no network
     access and may not create a confirmation on behalf of a person. A phase that
     records an action records a named system actor and an audit row.
   - The existing post-SQL steps are phases of this kind. They move into the registry
     when they next change; they do not have to be rewritten for this ADR.
4. **Readiness.** The baseline contract, vector health, every required phase
   complete, then the schema state for this release. Only this stage marks the
   database ready for the release.

### Phase inputs

A phase that needs operator data declares a versioned JSON input. It is supplied as
`--phase-input <phase-id>=<file>`; a phase may add a named alias, such as
`--secret-destinations-file`. Preflight validates every supplied input against the
current database:

- unknown fields are rejected;
- duplicates are rejected;
- identifiers must match real objects;
- fingerprints must match the current configuration.

An entry that no phase consumes is an error, not a warning. Inputs never contain
secret values. A missing required input blocks preflight, and the report names
exactly what is missing.

### Previous-release processes

Before stage 2, no runtime process of any release may hold a database session:
app, worker, scheduler, and on Scalable every service.

- Every runtime role sets PostgreSQL `application_name` to
  `flow-steward:<role>:<version>`.
- Preflight and stage 2 refuse while any session other than the upgrade's own
  carries that prefix.
- Sessions without the prefix (an operator's `psql`, backup tools) are listed in the
  report and do not block.
- A role that must stay up during maintenance (a status page) may hold a database
  session only if it identifies itself as `flow-steward:maintenance:<version>`
  and writes nothing.

`--maintenance-confirmed` stays as the operator's statement that a backup exists;
it no longer stands in for this check.

### Not serving before readiness

A runtime process of this release does not serve requests or take jobs until
stage 4 has recorded readiness for its version. It reports `database_upgrade_required`
on health and exits on a worker or scheduler role.

### Older releases refuse a newer database

Every runtime role checks at startup, not only the installer, that the database
holds no migration or phase this release does not know. If it does, the process
refuses to start, names what is unknown, and points to the restore of the backup
taken before the upgrade.

### Recovery is forward only

- After stage 2 has committed any file, recovery means running the same release's
  upgrade again. A failure in stage 3 or 4 is fixed and the same command rerun.
- Going back to the previous release means restoring the backup that preflight
  required. It never means starting the previous release on the migrated database:
  the startup refusal above makes that impossible rather than merely discouraged.
- An unknown in-progress marker, or a partially recorded phase, blocks automatic
  reruns. The operator inspects `flow-steward database status --json` and resolves it.

### Fresh installs and the 1.0 baseline

- A fresh install loads `db/schema/`, applies every migration (idempotent, per the
  amendment), runs every phase (each must be a no-op on an empty database), and
  passes readiness. Fresh and upgraded databases must reach the same schema and
  phase state. A contract test checks this for every release.
- At 1.0, `db/schema/` stays the baseline. Migrations shipped on the 0.9.x line stay
  in `db/migrations/` and in `db/released_migrations.json` for as long as any 0.9.x
  release is a supported source. Removing them requires a decision that drops that
  source.

### What this changes in ADR 0012

- "Pre-1.0: change the baseline without a migration" ends for released baselines;
  the 2026-11-01 amendment's rule applies.
- The ban on per-migration Python is kept for migrations. Data phases are a
  different, enumerated artifact with the limits above. They are not a migration
  format.
- Operator confirmation of stopped writers is replaced by the session check.

Manual `ALTER` on any installation is not an upgrade path.

## Verification

- Preflight writes nothing (compare a database snapshot before and after) and blocks on:
  - an unknown schema, drift or an unknown phase;
  - a live `flow-steward:*` session;
  - a missing or invalid phase input.
- A second concurrent upgrade fails at once.
- Stopping at each stage boundary and rerunning finishes once: no duplicate
  phases, no duplicate audit rows.
- A phase that fails leaves no completion row and no partial data.
- A previous-release image started on the upgraded database refuses to start, on
  both profiles.
- A process of this release refuses to serve before readiness.
- Upgrades from the previous published tag on Compact and Scalable reach the same
  state as a fresh install.

## Consequences

- Schema and data changes after a release become reviewable, ordered and resumable
  on both profiles, without manual `ALTER`.
- Some changes stop the upgrade until the operator supplies data, and preflight says
  so before anything changes.
- Runtime roles gain a startup check and a session name. The upgrade gains a phase
  table and a preflight mode. These are implemented by the first change that needs
  a data phase: the secret catalog (PR 2a). This ADR alone adds no code.

## Alternatives Considered

- **Keep changing the baseline only.** Rejected: installed databases never see the
  change (the 0.9.6 → 0.9.7 OAuth tables).
- **One transaction for SQL and phases.** Rejected for now: the runner commits
  per file, non-transactional files exist, and phases call application code that
  manages its own connection. Durable stage markers give resumability without that
  rewrite.
- **Computing fingerprints in SQL.** Rejected: two implementations of one
  security-relevant function drift apart.
- **Trusting `--maintenance-confirmed`.** Rejected: maintenance mode leaves the
  previous release connected.
