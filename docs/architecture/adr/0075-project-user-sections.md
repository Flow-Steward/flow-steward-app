# ADR 0075 UI разделы проекта поверх запуска и истории workflow

Status: Proposed

Date: 2026-11-18

## Решение

Добавить в core настраиваемые разделы проекта на существующих React-компонентах
форм и таблиц. Раздел связывает форму с одним workflow и показывает его jobs.
Основная работа относится к UI и сохранению настроек представления; выполнение,
идемпотентность, история и хранение файлов используют существующих владельцев.

Администратор сохраняет текущий интерфейс управления. Операторы видят общую
историю запусков выбранного workflow в проекте в рамках действующих полномочий.
Это соответствует командной области доверия [ADR 0066](0066-global-roles-and-secret-provider-boundary.md).
Политика личного владельца, extension, новые эндпоинты, новое файловое
хранилище и отдельный durable-механизм приёма пачки в эту функциональность не входят.
Существующие ограничения account, tenant, ресурсов и токенов сохраняются.

## Роли

Разделы опираются на чёткое разделение глобальных ролей, которое этот ADR
вносит поправкой в [ADR 0066](0066-global-roles-and-secret-provider-boundary.md#amendment-2026-11-18-proposed-in-adr-0075-admin-configures-operator-works-viewer-reads):

| Роль | Что делает |
|---|---|
| Admin | Всё, что настраивает систему: пользователи, расширения, проекты, workflow, триггеры, подключения, привязки и одобрение секретов, разделы. Видит административный интерфейс |
| Operator | Свою работу в разделах: запускает workflow, загружает файлы, проверяет результат и принимает решения approvals, смотрит историю. Может ввести или заменить значение секрета, например пароль почты, не меняя его привязку. Административного интерфейса не видит |
| Viewer | Те же разделы и история только для чтения, без действий. Например, аналитик или руководитель |

Права одинаковы во всех каналах: что роль может сделать в UI, то же она может
через API и MCP, и не больше. Личный токен действует с ролью своего владельца.
MCP нужен, чтобы работать из любого клиента, например с телефона, не открывая
продукт, а не для других полномочий.

Подключение бухгалтерской системы, выбор подключения для workflow и его
бизнес-логика относятся к настройке и остаются у администратора: их делает
специалист, который настраивает workflow и знает, какие методы API он вызывает.

## Как администратор настраивает раздел

Во вкладке проекта «Пользовательские разделы» администратор:

1. Задаёт название раздела, положение в меню и видимость; выбирает workflow
   из существующих привязок проекта.
2. Настраивает форму на основе контракта входов: порядок, подписи, подсказки
   и совместимый вид поля. Строку можно показать как input или textarea,
   перечисление — как select, boolean — как checkbox, файл — как загрузку.
   Описанные объекты и массивы отображаются группами и повторяемыми полями;
   произвольный JSON-текст от пользователя не требуется.
3. Выбирает режим отправки и, для For each, перебираемое поле и передачу
   одного элемента в контракт workflow. Остальные значения формы повторяются.
4. Выбирает колонки из свойств job, входов и объявленных выходов, задаёт
   подписи, порядок и формат отображения. Структуру данных определяет контракт
   workflow; настройки раздела её не дублируют. Вложенный путь доступен только
   при описанной структуре; свободный object или array её не подразумевает.

Настройки предлагается хранить в `projects.config.user_sections`, со ссылками
на workflow из `project_workflows`. Последний является отдельной таблицей,
а его представление в runtime-конфигурации не становится вторым источником
привязок. Чтение и сохранение настроек подключается к существующему изменению
проекта (`PUT /api/projects/{id}`), сохраняя остальные ключи config. После
разделения ролей этот маршрут доступен только администратору, поэтому
отдельный маршрут для настроек разделов не нужен. Новые таблицы и миграция
для этого не нужны.

Если workflow раздела отвязан от проекта, выключен или его контракт больше
не содержит поле, на которое ссылается раздел, раздел показывает понятную
ошибку и не принимает новые отправки; история остаётся доступной.

## Что видят оператор и viewer

Оператору в проекте доступны настроенные разделы, форма отправки, общая таблица истории
и просмотр входов, результата и файлов запуска. Например, «Входящие инвойсы»
показывает дату, документ, поставщика, сумму и статус. Поля результата появляются
после завершения соответствующего job. Используются существующие компоненты,
в том числе на мобильном экране с загрузкой фотографии чека.

История выбирается по проекту и workflow; при необходимости — по статусу,
датам и типу вызова. UI-запуски имеют `task_source=manual_ui`. Тип вызова
не идентифицирует конкретный раздел: несколько разделов одного workflow
могут показывать одни и те же jobs. Колонка «Кто отправил» информационная
и не ограничивает видимость. Viewer видит те же разделы, историю, результаты
и файлы без формы отправки и действий; его права на запись не появляются.
Оператор и viewer получают навигацию по разделам вместо административного меню;
сервер проверяет права независимо от того, что показано в меню.

### Группировка меню по проектам

Навигация оператора и viewer автоматически зависит от числа доступных
пользователю проектов с видимыми настроенными разделами:

- Если проект один, его разделы отображаются на верхнем уровне меню,
  без дополнительного родительского пункта с названием проекта.
- Если проектов несколько, название каждого проекта становится родительским
  пунктом раскрываемой группы, а его разделы — вложенными пунктами меню.
- Проекты без видимых разделов не создают пустых групп и не влияют на выбор
  между плоским и сгруппированным меню. Если разделов нет, показывается
  пустое состояние.

Пункты используют настроенные названия разделов, связанных с workflow,
а не весь каталог workflow проекта. Группировка не требует отдельной
настройки администратора и не меняет адрес раздела: проект остаётся частью
его идентичности и при отображении на верхнем уровне.

## Режимы отправки

| Режим | Выполнение | История |
|---|---|---|
| For each | N обычных запусков, по одному на элемент; свой стабильный ключ идемпотентности на каждый элемент при повторе той же отправки | N jobs, у каждого свой статус и результат |
| Bulk | Один обычный запуск со всеми значениями формы, совместимыми с контрактом workflow | Одна job с общим статусом и результатом |

Режим задаёт администратор. Для чеков выбирается For each: пользователь
выбирает пачку, UI отправляет отдельные запросы с ограниченной параллельностью
и показывает, какие из них приняты и какие завершились ошибкой отправки.
Повтор того же запроса использует прежний ключ; намеренная новая обработка —
новый. Закрытие браузера не гарантирует отправку оставшихся элементов.
Отдельного серверного журнала пачки, атомарности всей отправки и автоматического
восстановления неотправленных элементов нет. Принятые jobs выполняет текущая очередь.

Вход каждого запуска проходит существующую валидацию. Если контракт требует
массив, For each передаёт одноэлементный массив, только когда это допускают
его ограничения. Файловый вход получает настоящий загруженный файл.
Bulk коллекции файлов в одном входе пока не поддержан прямой привязкой:
его нужно либо дополнить поверх существующего хранения артефактов, либо
сделать этот вариант недоступным. Увеличение лимита байтов само это не решает.

## Необходимые доработки

1. **Запуск для operator через существующий маршрут.** Форма раздела вызывает
   тот же `POST /api/workflows/{id}/run`, что и Builder, с ревизией,
   идемпотентностью, UI-каналом и проверками ресурсов. Нужны две правки:
   исключение для этого маршрута в middleware (сейчас запись в `/api/workflows/...`
   разрешена только admin) и проверка роли в самом маршруте (сейчас только admin).
   Подтверждение реальных эффектов форма раздела отправляет от имени оператора
   при отправке; администратор подтверждает их при публикации раздела.
2. **Разделение ролей в middleware.** Запись по умолчанию разрешена только admin;
   operator получает явный список: запуск workflow, решения approvals,
   отмена и повтор jobs, значения секретов и действия своей учётной записи.
   `PUT /api/projects/{id}` становится admin-only; это также закрывает
   нынешний обход, при котором operator через него меняет привязки workflow
   и политику проекта, хотя `PUT .../workflows` и `PUT .../policy` требуют admin.
3. **Лимиты реальной загрузки.** Подключить существующую конфигурацию
   ограничений вложений к UI-запуску. Согласовать лимит декодированных байтов,
   ограничение длины base64 и проверку frontend: сейчас в них зашит 1 MiB.
   `FS_WORKFLOW_TEST_FILE_MAX_BYTES` относится к тестовым файлам;
   реальные загрузки должны учитывать `FS_ATTACHMENT_MAX_SIZE_BYTES`
   и действующую политику количества и типов вложений.
4. **Автор запуска при необходимости колонки.** Записывать подтверждённую
   личность из scope в `jobs.meta`, не принимая её из полей формы.
   Это отображаемые метаданные, а не новая политика владения. Миграция не нужна;
   у старых jobs значение может отсутствовать.
5. **Связать UI с существующими данными.** Добавить сохранение конфигурации
   разделов в JSON проекта через изменение проекта и разрешить поддержанные значения фильтра
   `task_source`, включая `manual_ui`, в API, query service и frontend.
   В БД колонка и фильтрация уже есть, но публичный API сейчас разрешает
   только `workflow_test_run`.

Файлы уже сохраняются как артефакты job через `_persist_file_refs`;
новый способ хранения не вводится. Backend-логика остаётся в прикладных
сервисах, маршруты — тонкими адаптерами, UI — в `assets/frontend/`.
Работа считается готовой, когда раздел сохраняется администратором и открывается
оператору и viewer, For each и совместимый Bulk создают обычные jobs, фото проходит
настроенные лимиты, история и её фильтры работают в общей командной модели,
а operator и viewer получают отказ сервера на любую запись вне своего списка.
