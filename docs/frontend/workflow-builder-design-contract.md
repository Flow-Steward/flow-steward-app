# Workflow Builder: термины и контракт переноса дизайна

Этот документ задаёт общие термины, композицию и полные action→controller→guard→persistence flows Workflow Builder. Для задач переноса дизайна его читают вместе с `design-system.md` и canonical frontend standard; инженерные правила остаются в `AGENTS.md` и `docs/standards/*`. Matrix и scoped owner tasks определяют работу и статус. Принятый source artifact, design intent или опубликованный guide не означают принятого продукта. Whole-workflow Form Dialog rule и этот guide публикуются согласованно; contextual Step Test Run и shared Interface rules сохраняются.

## Термины, которые нельзя смешивать

| ID | EN UI term | Значение и граница |
|---|---|---|
| T01 | Workflow | Определение процесса с реальными persisted revision, contract, steps и containers. Не изображение canvas и не один job. |
| T02 | Step | Узел текущего schema kind; source/action/parameters/outcomes берутся из реального каталога. Историческая таблица типов не ограничивает все kinds, поддержанные текущими schema/catalog; постоянный glossary не фиксирует их число. |
| T03 | Group | Одноразовый container. Sequence/lanes, entry/members/exits следуют текущей schema. Не loop и не прежняя Phase. |
| T04 | For each | Самостоятельный container в `for_each`, со source/item/index/body и допустимой concurrency. Не inline step kind и не Group kind=loop. |
| T05 | Lane | Именованная дорожка parallel body текущего container. Её ID, membership и exit нельзя угадывать из позиции карточки. |
| T06 | Hook | Явно объявленная автором workflow зона: место на canvas, куда каждый project добавляет свои шаги (решение R2-11, 2026-10-22). Объявление зоны и её заполнение — разные операции. UI никогда не показывает workflow за Hook: нет выбора «Workflow to run here», mapping, Check/Connect/Disconnect, «Create and connect» и имён вида «#2». Шаги хранятся в скрытом per-project workflow, который создаёт первый Add через create-and-bind: пустой, только скрытый конец `hook_end` (`stop_success`, entry), который canvas не рисует. Новый Hook пуст (бейдж Empty); пустой Hook пропускает входы без изменений. Шаг, ведущий в `hook_end`, рисуется как выход к концу рамки (End of the hook); первый узел пустого Hook становится entry и ведёт к концу; без узлов entry снова `hook_end`. «Clear the hook» снимает все шаги одним unapplied изменением (Undo/Discard возвращают). Повторно используемая логика — шаг Invoke workflow внутри Hook. Без выбранного project Add step заблокирован с причиной; header builder предлагает связанные projects. Ordinary developer-owned shipped core остаётся read-only. Это визуальная композиция Hook, не domain Group/For each и не отдельный step kind. Аналогия callback/event не вводит event bus, новый Trigger catalog type или Automation reaction. |
| T07 | Optional | Семантика optional шага/поля по schema. Не команда Disable; нельзя добавлять выдуманный disabled-node режим. |
| T08 | Save parameters | Завершение редактирования параметров в **своём lifecycle**. Existing saved step без затрагивающей его structural операции может выполнить реальный revision-guarded `update_step_config` API. New/local/staged step, staged kind/outcome change может только обновить canonical change-set draft до Apply. Не обещать серверное сохранение для всех веток. |
| T09 | Apply changes / Structure not applied | Публикация canonical staged structural/config operations с expected revision, validation/conflict handling. Для hook+author используется существующий composite Apply: child, затем author. Не автозапуск Test Run. |
| T10 | Structure applied | Текст состояния, не ещё одна кнопка. Не утверждает отсутствие всех unsaved parameter/contract drafts. |
| T11 | Applied snapshot | Реальная applied workflow definition/revision, зафиксированная при запуске. Не несохранённая форма, выбранная карточка или installed extension version. Последующие edits не переписывают run. |
| T12 | Test Run | Настоящий job процесса с project/revision/input guards. Не sandbox внешних эффектов, не демонстрационный таймер. |
| T13 | Step Test Run | Реальный отдельный запуск выбранного применённого шага со своим cursor/input bindings. Не произвольный subgraph resume и не повтор старого run. |
| T14 | Selected run / Latest run | Выбранная historical identity и последний run различаются. Canvas, run bar и Results показывают одну согласованную identity/snapshot; Back to latest возвращает к актуальному. |
| T15 | Pass / occurrence | Конкретное выполнение шага, в том числе loop item/lane/attempt по реальным records. «Latest output» относится к реальному pass, не автоматически к последнему изменённому node. |
| T16 | Keep output / Kept | Test-only сохранённые outputs finished pass или валидированный manual JSON по declared outputs. Не optional skip, не mock реального production run, не host effect-suppression output. Для этого нужен опубликованный test-output persistence/runtime contract; browser-only подмена не заменяет capability. |
| T17 | Approval / Review request | Ожидание решения с настоящим approval ID, вопросом, values этого run и destinations. Не безусловная кнопка Approve рядом с launcher. |
| T18 | Required | Конкретное требование schema: наличие ключа, значение, type, enum или nonempty — разные проверки. Required key не всегда значит nonempty string. `false`, `0`, допустимые `""`, `[]`, `{}` нельзя потерять через truthy filtering. |
| T19 | Fixed default / Test file | Значение/файл, заданные контрактом для ревизии. Caller не отправляет forbidden override. Configured secret показывается как configured, не раскрывается. File test input следует настоящему attachment contract. |
| T20 | Trigger / Provider trigger | Вход запуска извне: incoming webhook или событие подключённого extension app. Не Automation reaction после события runtime и не Schedule. |
| T21 | Schedule | Отдельная сохранённая сущность в project, запускающая связанный workflow по cron/timezone. Save workflow settings не создаёт и не включает Schedule. |
| T22 | Automation rule | Runtime reaction в scope workflow/step/group с reaction key, event/action/target. Не before/after Hook. Switch меняет сохранённое enabled; другие draft fields ждут Save rules. |
| T23 | Ready / Off / Needs setup | Human presentation readiness конкретной сущности. Disabled не значит invalid; enabled не доказывает readiness. Использовать реальную server taxonomy/authority, не слепо унифицировать webhook и provider по prototype. |
| T24 | Development Environment / Production | Целевой authoring contract: в Production нельзя создавать новые hook declaration identities (declared zones). Это environment-ограничение не вводит нового запрета на уже разрешённые policy редактирование, удаление и перенос существующих declarations в personally editable workflows. Filling/binding существующих hooks собственной логикой доступны в обоих режимах по действующей policy/capability; protected extension-owned core остаётся read-only в обоих режимах. Не предполагать существование конкретного feature flag/API: UI потребляет опубликованную policy/capability, в том числе для Development authoring. |

## Границы Group / For each и объявление Hook

**Container boundary** — настоящий Group или самостоятельный For each может иметь optional `boundary_contract.entry`/`.exit` для данных входа/выхода. Graph `entry`, связи к `group_exit`/`for_each_exit` и outcome-порты задают порядок выполнения, а не этот контракт. Runtime проверяет контракт фактического container в pinned definition, не похожей рамки canvas. Для required входа `0` и `false` присутствуют; правила null/пустых значений у входа нельзя автоматически переносить на выход.

**Доступ и проверка сейчас.** В Builder inspector нет отдельной формы или общего JSON editor для этих полей. Их можно задать через авторизованный revision-guarded `/changes` API или импорт целого workflow YAML; Save иных настроек не должен молча менять сохранённый контракт. Shape/selector проверки охватывают оба container вида, но row-level readiness For each не следует считать полной копией Group без отдельного доказательства. Это не обещание готового UI или нового schema.

**Hook — другое объявление.** Group-like Hook на canvas остаётся Invoke-зоной с JSON Schema `input_schema`, `input_mapping`, `mutable_fields`, `additional_outputs` и скрытым binding/output mapping, а не `boundary_contract` рамки. Passthrough/override Hook определяется наличием ключа: разрешённые `""`, `0`, `false`, nullable `null` сохраняются; результат, который шаги не задали, сохраняет вход того же имени. Визуальное сходство не делает два контракта одним.

## Данные Hook: входы, замены и отдельный результат

Автор объявления задаёт typed `input_schema`/`input_mapping`, разрешённые для замены `mutable_fields` и output-only поля `additional_outputs`. Binding связывает inputs/outputs child с этим контрактом. Типы, required, nullable и ограничения берутся из JSON Schema; вход, не включённый в `mutable_fields`, остаётся read-only для output mapping. Визуальная typed form должна отражать этот контракт, а её наличие не следует из наличия backend schema. [T06; current hook contract]

**Passthrough** — сохранение опубликованного входа в результате hook, если для этого поля нет override. Unbound hook не запускает child; child с логикой только побочного действия (например, отправки письма), без output overrides, также оставляет входы неизменными. Output-only поля дополняются declared defaults; optional поле без default и без значения остаётся отсутствующим. Это не отключение Hook и не создание пустого значения вместо отсутствующего ключа.

**Хранилище шагов Hook (R2-11).** Первый Add создаёт enabled callable workflow: входы — поля Hook `input_schema` (`fields`), outputs — каждое `mutable_fields` и `additional_outputs` поле как optional `variables` output, связанное с полем Hook того же имени; граф — только `hook_end`. Пока в нём только `hook_end`, runtime ничего не запускает и публикует входы и defaults, как unbound Hook. Readiness не требует «real execution» шага от такого workflow (Hook только из Set variable меняет результаты), а optional output, который не задаёт ни один шаг, — warning, не error. Project ownership, binding revision, idempotent retry, authorization и chain limits остаются действующими; automation (API/CLI/MCP/import) может по-прежнему связать Hook с любым callable workflow.

**Override** определяется наличием ключа, а не truthiness: явные `""`, `0`, `false` заменяют mutable input, если разрешены его schema; `null` заменяет только при nullable schema. Результаты читаются по имени из state Hook в его конце: если binding содержит mapping `child output → hook target`, а шаги не задали source key, поле сохраняет вход того же имени (output-only поле — declared default), а не `workflow.hook.mapped_output_missing`; значение неверного типа по-прежнему ошибка. Немаппированные child outputs не становятся автоматически hook outputs.

**Published Hook output** — отдельный `state.hooks.<hook_id>.output`; исходные author variables не меняются. Например, input `company_name` читает `state.invoice.company_name = "Example UAB"` и разрешён в `mutable_fields`. При отсутствии override результат содержит `"Example UAB"`; mapped child value `"EXAMPLE UAB"` публикуется как `state.hooks.before_invoice.output.company_name`, тогда как `state.invoice.company_name` остаётся `"Example UAB"`. Имена примера иллюстративны, canonical namespace остаётся `state.hooks.<hook_id>.output`. Последующий шаг явно выбирает исходный либо hook result selector. Весь результат проверяется до атомарной публикации; invalid output не должен выглядеть успешным частичным результатом.

Одна и та же рамка поддерживает callback-like side effect без overrides и filter/transform разрешённых данных с published output. Protected developer core и объявленная граница доступных данных сохраняются в обоих случаях. [current `workflow_hook_contract.py`: `select_hook_targets`, `normalize_hook_output`; `invoke_workflow_hook_runtime.py`: `publish_hook_output`]

## Единая композиция, разные зоны ответственности

**Header** — верхняя строка Builder. Нормативная высота64px, нарисованные controls32px; Back/title, Interface, plain structure status, Apply, validation, More располагаются по Main reference. Не добавлять отдельную Info-панель/дублирующую широкую contract strip. Start показывает summary Inputs и launch channels и ведёт к shared Interface Inputs; он не становится владельцем всего Triggers editor. Stop success показывает summary/navigation Outputs (переменные и возвращаемые файлы) и открывает shared Interface Outputs; табов Artifacts и External changes нет (ADR 0039). Полные Triggers/Schedules forms остаются в Workflow settings со своими persistence owners; полный контракт также доступен через Interface. Геометрия не оправдывает удаление реального callback или guard. [CANVAS Main/Start; shared Interface contract]

**Canvas toolbar** — центрированная плавающая нижняя панель высотой 42px, с отступом 16px снизу, а не footer формы. Ровно 10 controls слева направо: **Step → Group → Search → Auto layout → Failure paths (иконка/count) → Zoom out → Zoom percentage/reset100% → Zoom in → Fit → Test Run**. Auto layout tooltip объясняет сброс manual placements; viewport/scope actions вызывают настоящие callbacks. Minimap включена по умолчанию и расположена отдельно: это не 11-й control toolbar, она не перекрывает панель. Не оставлять старые вертикальные viewport controls и orphan actions. Убирается только workflow-level Test Run tab в Workflow settings; **contextual Step Test Run tab в step editor сохраняется**. Whole-workflow Test Run не возвращается в Header. [CANVAS Main/Canvas; DOC04 §Сценарий; DOC06 §«+»]

**Drawer** — немодальная правая contextual panel. Header/tabs/body/footer принадлежат текущему editor context; только допустимые вкладки/поля/действия. Close убирает panel из AX/keyboard reachability, сохраняет положенный draft lifecycle и возвращает фокус. Hidden translate без `inert`/реального удаления не считается закрытием. Protected ordinary editor read-only, hook editor editable по своим данным. [CANVAS Panels; protected workflow/hook contract]

**Form footer** — нижняя зона конкретной формы Drawer/Dialog: её Save/Cancel/status, не canvas toolbar. Список Triggers footer не имеет; footer появляется внутри формы. Automation footer содержит только Unsaved changes и Save rules; Add rule расположен под списком. Schedule form имеет собственные Cancel/Create/Save и не сохраняется кнопкой Save workflow settings. [DOC02 §§список/сохранение; DOC03 §форма; DOC05 §список]

**Form Dialog** — блокирующее решение «запустить или отменить» поверх всего Builder. Whole-workflow launch использует shared `DsDialog variant="form"`:номинальные 600px Medium, radius 12px, content-driven height, ограниченная viewport; header padding 16px 24px, body padding 16px 24px 24px, footer padding 12px 24px. Header/footer остаются видимыми, скролл только у body;872/994px на static examples не являются fixed product height. Focus в первом изменяемом поле, Escape сначала закрывает popup, затем dialog; Cancel/X/backdrop возвращают focus trigger. Background должен быть реально изолирован: manual focus trap + aria-modal не равен автоматически native `showModal`/inert. Results — отдельный contextual Drawer, не длинный хвост внутри launcher. [DOC04 §§сценарий/модальное окно; DS `form-dialog.md`]

## Полный путь действия

**Individual Step Play.** Play в contextual strip **над выбранным/hover шагом** относится к отдельному Step Test Run, а не whole-workflow запуску. Контекстная кнопка «Test step»/Play открывает Step editor → Test Run tab; она сама по себе не доказывает submission отдельного job. Его entry point сохраняет разрешённый Step Test Run drawer/tab, current selected-step scope, input bindings, revision/local/dirty/protected guards и page-owned controller. Не перенаправлять его в whole-workflow dialog и не клонировать runner. Обычный protected шаг нельзя тестировать изолированно, если policy запрещает; пользовательская hook-логика использует свой child scope. [DOC04 §Сценарий; frontend standard: Step Test Run]

1. **Create / connect.** Step palette, свободный порт, drag-to-empty и Group/lane Add используют одну current creation/connection authority. Видимая карточка — canonical staged graph operation с правильной scope/lane/edge, без fake binding или descriptor-only demo. Cancel/Undo не стирают чужие drafts. Protected ordinary structure не меняется; в объявленной hook-зоне разрешено добавление собственной пользовательской логики: unbound first Add создаёт/связывает child по существующему контракту, последующие действия редактируют bound child. Это не разрешает редактировать ordinary protected core и не вводит новый inline-step storage ABI. [DOC06 §«+»; current creation/connection contract]

**Step palette — выбор типа шага.** Actions содержит ровно Agent, System Tools, MCP Tools, Extension Tools, Invoke workflow и HTTP request. Agent — один тип; конкретный агент выбирается в существующем setup. Три Tools — presentation categories существующего canonical `connector`, а не новые runtime kinds: после выбора в существующем drawer выбираются источник (tool/extension), затем operation и публичные параметры. Палитра не перечисляет отдельные agents, extensions, tools или catalog operations; общего Action step нет. Flow содержит If, Switch, Approval, Wait, Batch и For each; настоящий Group остаётся отдельно. Категория нового пустого tool draft хранится только в owner-scoped editor state до Apply/Discard/удаления своего creation intent и сохраняется при Close/reopen; она не сохраняется в workflow/API и не переопределяет реальную connector identity. После настройки сохраняются реальные source/install/operation identities и разрешённые falsy значения. [Прямое уточнение пользователя 2026-10-20; existing tool-category/setup contract]

2. **Edit → Save → Apply.** Поля и ошибки соответствуют actual full schema/validator; form dirty/save failure/invalid raw input остаются видимыми. T08 определяет, ушёл ли Save через API либо остался staged. Apply использует настоящие operations/revision/conflict/refetch, после успешного refresh снимает только соответствующий guard. Нельзя удалить существующую функцию ради нового расположения кнопки. [current `detail-step-actions.ts`, `detail-change-set.ts`, `detail-hook-scope.ts`; назначенный владелец Save ruling]
3. **Whole-workflow Test Run.** Нижний Canvas toolbar Test Run и совместимые URL aliases `?drawer=test-run` / `?drawer=workflow-test-run` открывают одну общую Form Dialog через прежний invalid-input guard, без submit при opening. Project берётся из настоящего контекста; no-project Choose/Link сохраняется, хотя в prototype этого состояния нет. Inputs — сохранённый contract, fixed/test-file правила; Summary и typed validation действуют по API. Dirty/unapplied author+child, new forms, saving/failed state, unavailable policy, missing required/project, pending и revision conflict не обходятся. Apply не запускает автоматически. Canvas, run bar и Results показывают согласованные real job identity/revision/snapshot/pass, без выдуманных duration или скрытых/секретных payloads. Stop/cancel/retry/restart сохраняют server lifecycle и authority; Run again различает fresh current-applied run и verified replay snapshot. Historical selection не переписывает current run. Принятый запрос на переход ещё не означает, что editor открыт: Results уступает ему место только после фактического guarded commit. Cancel, смена job/pass и поздний ответ не сбрасывают чужой parameter draft и не завершают старый переход.

**Run bar** — строка состояния выбранного проверенного Test Run над нижним **Canvas toolbar**; это разные элементы. Пустая idle-строка не показывается. Builder открывается с чистым canvas, если доступны только terminal/неизвестные прошлые runs; они открываются явным выбором через history существующей Test Run Form Dialog в Canvas toolbar. Проверенное активное выполнение видно и остаётся выбранным после завершения; current ACK и явно выбранный historical Result сохраняют согласованные status/marks/Results. Workflow-only storage/latest pointer сам по себе не выбирает terminal Result при reopening. History, ACK и storage не стираются, второй poller не создаётся. Stop подтверждает отмену выбранного активного job через server lifecycle и права admin/operator. Terminal × **Clear marks** снимает только локальный выбор и отметки: history и ACK/latest pointers сохраняются; тот же latest не выбирается немедленно снова без нового run или явного выбора. History показывает реальный статус, записанное время и доступную duration; UUID остаётся дополнительной идентичностью. Run-level failure не означает, что успешно выполненная операция Stop fail должна получить failed execution status.

**Run again** — новый Test Run текущего applied workflow через тот же launch controller, project/revision/dirty/validation/single-flight guards и ACK flow. Прямой старт использует только immutable public inputs последнего принятого в этой сессии job, если выбран именно он и контракт совместим; secret/неподдержанные inputs, иной history job, reload или несовместимость открывают существующую Form Dialog без прямого запроса. Чужой draft формы не выдаётся за исторические inputs и не перезаписывается; после отказа reusable inputs показывается scoped причина, а field errors относятся только к совпадающим значениям. Verified restart остаётся отдельным server replay действием. У проверенного активного выбранного run нижний Canvas toolbar показывает **Running** с DS Loader и открывает guarded Results; idle Test Run сохраняет существующий launch link и Form Dialog.

## Границы дизайна и runtime contract

Прямое уточнение пользователя от 2026-10-19: designer drawer — концепт, не полный список полей. В HTTP request и других формах макет может пропускать реальные настройки. Дизайн задаёт раскладку, действия и взаимодействия; полнота редактируемых полей, их типы, required/optional, defaults и conditional branches следуют актуальному публичному authoring-контракту backend, каталогу и policy. Сохранять **все** поддержанные пользовательские настройки, включая optional/Advanced, даже если их нет в prototype. Служебные/derived/read-only/capability-gated поля классифицируются явно и не становятся произвольными inputs; неизвестный backend payload не добавляется ради макета.

Прямое уточнение пользователя: системные/internal/backend-owned поля, которые заполняет backend, исключаются из пользовательского UI, а не превращаются в inputs или Advanced-настройки ради parity. Полнота относится к поддержанным пользовательским настройкам. В карте указывать классификацию и backend-источник исключения; отсутствие internal-поля в UI не является дефектом. Business read-only/derived/capability-gated информация оценивается по её продуктовому назначению и правам; наличие поля в API само по себе не требует его отображать. Не отправлять служебные значения как новые пользовательские параметры Save.

Для каждого drawer в матрице нужна карта «backend поле/вариант → UI control/секция → payload → readback» с источником и применимостью. Приёмка включает доступность каждого editable-поля пользователю, правильные conditional/required/optional и ошибки с фокусом, реальные Save/Apply и reopen без потери значений, включая пустые/falsy/null по schema. Проверять кликами в обеих темах на согласованных viewport. Отсутствие настройки в концепте не оправдывает её потерю; размещать её в согласованной DS-композиции, не урезая продуктовый контракт.

- Поле, объявленное persisted, должно поддерживаться настоящими read/create/update models и корректно восстанавливаться после reopen. Нельзя добавлять fake required field, неизвестный payload или скрывать backend-required поле ради копии prototype. Новая capability требует согласованного UI/backend contract.
- Auth modes, signature configuration, limits, readiness и secret lifecycle должны совпадать между UI, service и canonical schema. Макет не разрешает ослабить auth/TLS/SSRF или вручную менять чужую базу.
- Предупреждение о будущей ошибке не обходит server validation, dirty/revision/project/pending guards. Отсутствие состояния в prototype не позволяет удалить поддержанный продуктовый flow.
- Экспериментальные routing weights/thresholds не становятся критериями приёмки без утверждённого design contract. Semantic outcome order и manual positions сохраняются.
- Демонстрационный таймер, Undo или provider preset не доказывает backend persistence/restoration/credential safety. Catalog и outputs берутся из настоящих capabilities и records.

## Просмотр дизайна и проверка поведения

Для полного interactive preview designer Main используется верхний правый Workflow/Play. Это control просмотра дизайна, а не Header Test Run продукта. Просмотр prototype не заменяет проверку приложения с настоящими controllers, guards и persistence.

Проверка выполняется отдельно в light/dark и на согласованных viewport, включая1461×806 и1280×800:

- Нижний Test Run открывает общую Form Dialog; Cancel/Escape/focus return, Apply/revision/dirty/project/pending guards работают, duplicate job не создаётся. Header whole-workflow launcher отсутствует.
- Успешный whole-run submission автоматически открывает Results того же job. Canvas active status/elapsed, полная execution chain и раскрываемые input/output/log/status/timing относятся к правильным run/pass; secret masking сохраняется.
- Contextual Test step/Play над выбранным/hover шагом открывает отдельный Step editor Test Run tab; реальный execution action сохраняет step-specific authority и scope.
- Пустой declared hook (Empty) принимает первый шаг в выбранном project и не показывает workflow; Hook с шагами редактируется на canvas, «Clear the hook» снимает их одним изменением. Protected extension-owned ordinary core остаётся read-only в обоих режимах. Environment gate запрещает новые hook declaration identities в Production, не вводя дополнительной заморозки уже разрешённых personal edit/delete/move существующих declarations. Заполнение существующего hook шагами сохраняется в обоих режимах по действующей policy/capability.
- Hook data: в обеих темах проверить пустой Hook (passthrough), mutable transform в отдельном published output при неизменных author variables, `""`/`0`/`false`, nullable/null и read-only errors. Результат, который шаги не задали, сохраняет вход (или default), а не `workflow.hook.mapped_output_missing`. Save/reopen восстанавливает настоящий declaration/binding contract.
- Hook canvas: видимая пустая рамка с Add (заблокирован без project, с причиной) и рамка с несколькими custom steps/Invoke; конец рамки — End of the hook; создание/выбор/редактирование/Clear сохраняют hook child scope, protected core и различия Group/For each; после Clear старые шаги исчезают сразу и не возвращаются при следующем Add.
- Start/Stop summary navigation открывает shared Interface forms; полные Triggers/Schedules forms и их persistence flows остаются доступными.
- Dialog при длинном содержимом ограничен viewport; header/footer видны, scroll только у body, padding16/24/24; drawn32px controls и coarse44px hit areas не смешаны.

Дизайн-источник описывает intent; статический source или отдельный тест не заменяет независимую браузерную проверку полного action→controller→guards→persistence→reopen пути.
