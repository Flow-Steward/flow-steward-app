# CLI user experience: human-first output, quiet installers, completion

Status: in progress (started 2026-11-09). Done: phases 1-5 in code; verification next.
Branch: `claude/cli-ux-20261109`, cut from public `main` 0.9.13 (`1755bdf`), kept apart from
the 0.9.14 release batch and rebased onto `main` after that batch merges.

## Why

The management CLI works, but reading it is hard:

1. **Commands answer in JSON nobody asked for.** The default renderer is plain, and the plain
   renderer has a human layout for five commands only (`status`, `doctor`, `users list`,
   `extensions create`, `stack logs`). Every other command falls through to
   `json.dumps(result)` on one line (`core/entrypoints/cli/platform/renderers.py`,
   `PlainRenderer.render_result`). The impact plan shown before a confirmation is JSON too.
2. **Colour is opt-in.** `select_mode` enables colour and Rich only with `--tui`
   (`core/entrypoints/cli/platform/modes.py`). Mature CLIs do the opposite.
3. **`--tui` was switched off by the owner because the full-screen Textual form is confusing:**
   every field on one screen, choices as checkboxes, Confirm/Cancel/Advanced buttons, mouse
   enabled, focus that jumps. Its Rich result renderer still prints nested values as JSON.
4. **The installer buries its result.** `installer.py` streams every line of Docker build/pull/
   compose output unless `--json` is set (`stream_output=verbose or not json_requested`), and
   `install.sh` tees the installer image build to stderr. The setup link and URL scroll away.
5. **Hints cannot be pasted.** About 260 hint strings say `flow-steward ...` and 78 say
   `./flow-steward ...`. On a Docker host only `./flow-steward` works; in the Compact image on a
   platform (Railway, Render) only `flow-steward` works.
6. **No Tab completion.** Users retype and remember commands.

## Principles (how mature CLIs do it: gh, Railway, Vercel, Fly, Stripe, uv, rustup, clig.dev)

- Human output by default. Machine output only with `--json`. Redirected output is plain
  lines, never JSON unless asked.
- Colour on by default in a terminal; off for `--no-color`, `NO_COLOR`, `TERM=dumb`, pipes.
  Colour carries meaning: green ✓ success, red ✗ failure, yellow ! warning, dim = secondary.
- A change prints one result line, the key facts and the next step — never the whole object.
- Lists are borderless aligned tables with the key columns; `show` prints a key/value card.
- Long operations show 5–8 named steps with spinner → ✓ and elapsed time, real progress
  (n/m, bytes) instead of a heartbeat, technical output in a log file (on screen only with
  `--verbose`), and a final summary block that is the last thing on screen. A failure names
  the step, shows the last lines of that step's output, the one fix and the log path.
- Ask everything first, one question at a time, in the normal terminal flow (no full-screen
  forms, no mouse). End with a review and the equivalent command with flags.
- Every hint is a command that runs when pasted where it was shown.
- Everything works in a bare provider console with no Docker and possibly no TTY.

## Command kinds

Every public command declares one presentation kind. One renderer per kind produces the
coloured and the plain form from the same data, so 130 commands need no per-command branches.

| Kind | Commands (examples) | Output |
|---|---|---|
| `table` | `users list`, `jobs list`, `extensions list`, `backup list` | title, aligned columns, paging hint |
| `record` | `users show`, `jobs show`, `config show`, `release info` | title, key/value card, sections |
| `action` | `users create`, `maintenance enable`, `config set`, `jobs cancel` | `✓ <what happened>`, key facts, next step |
| `operation` | `install`, `release upgrade`, `backup create`, `stack rebuild`, `clone create`, `database upgrade` | plan → steps → summary block, log file |
| `report` | `status`, `doctor`, `validate`, `quality *` checks | sections of findings with status marks and remediation |
| `stream` | `stack logs`, `jobs logs` | raw lines |
| `document` | `reports diagnostics`, `workflows export`, `proxy-fragment` | the artefact itself on stdout, status on stderr |

## Phases

Each phase is one or more commits on the branch, verified before the next starts.

### Phase 1 — human output for every command (this branch starts here)

- `presentation` kind + display fields (columns, card fields, success message, next-step
  template) on `CommandSpec`; a guard test fails when a public command has none.
- Kind renderers in `core/entrypoints/cli/platform/`; coloured (Rich) and plain variants.
  Nested values render as indented key/value lines, never JSON.
- Colour on by default for a terminal; `--plain` = no colour, no animation, same layout;
  `--tui` no longer affects output. Impact plans render as a readable list of effects.
- One `cli_command(...)` helper builds every command shown to a user from the invocation
  prefix the launcher passes (`./flow-steward` on a host, `flow-steward` in the Compact image);
  a guard test forbids hand-written `flow-steward` command strings in user-facing text.
- ADR amending ADR 0017 items 3–5 and `docs/contracts/cli.md` (default presentation).

### Phase 2 — long operations

- Installer and `release upgrade`, `backup create|verify`, `clone create|restore`,
  `stack rebuild|restart`, `database upgrade`: named steps, technical output to the log only
  (`--verbose` streams it), failure block (step, last lines, fix, resume command, log path),
  final summary block (URL, sign-in link, config location, next commands); warnings collected
  into the summary.
- `install.sh` stops teeing the installer image build to the terminal.

### Phase 3 — inline input instead of the full-screen form

- Replace the Textual full-screen form with sequential inline questions: arrow-key select with
  type-to-filter, masked secrets, Esc = back, keyboard only, works at any terminal size.
- Review summary, then the equivalent non-interactive command line.
- Library decision recorded in the ADR (Textual inline mode vs prompt_toolkit; ADR 0017 item 9
  currently excludes Questionary/InquirerPy).

### Phase 4 — shell completion

- `flow-steward completion bash|zsh|fish` prints a static script generated from
  `PUBLIC_COMMAND_SPECS` (commands, subcommands, flags, fixed choices): instant, never starts
  Docker on Tab.
- The installer offers to install it; the Compact image ships it for provider consoles.

### Phase 5 — interactive mode

- `flow-steward` with no arguments in a terminal opens a prompt with Tab completion,
  descriptions while typing, and history. One runtime start per session, commands run
  in-process.

### Phase 6 — standards, documentation and wide verification

- `docs/standards/` rules for new commands (kind, hint helper, no raw JSON outside `--json`).
- Documentation, checked in all four places: the repository README, the in-repository
  docs (GUIDE, runbooks, contract, agent skills), the official docs site
  (docs.flowsteward.org) and its source in `flow-steward-doc` (5 pages still mention
  `--tui`); the site changes are published together with the release, not before.

Verification order (owner, 2026-11-09): local Compact and Scalable, then a disposable
stand on the Linux server that hosts the demo (the demo itself untouched, the stand
removed afterwards), then Railway with the installed console commands. Old shells such
as macOS bash 3.2 are out of scope: modern bash, zsh and fish only.

Every phase is checked by running the real commands, not only unit tests.

| Environment | How |

commits; one `--full` on the final commit before merge.

## Decisions taken without asking (change if wrong)

- `--plain` stays (no colour, no animation, same layout) for logs and screen readers;
  `--tui` is removed with the full-screen form (no compatibility alias before 1.0).
- Default for a terminal: coloured output; questions only when input is missing.
- Phase 3 uses prompt-toolkit for arrow-key choices (Textual removed from all images).
- Phase 5 is `flow-steward shell`: a bash session with the generated completion and
  history, every command run through the normal launcher -- so it reaches the right
  runtime on Scalable, where lifecycle and product commands live in different containers.
- Known pre-existing gap: `tests/integration/test_cli_vertical_slice.py` has no cases for
  `workflows.definition`, `database.preflight` and other newer commands (fails on main too).
