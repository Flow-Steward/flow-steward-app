# Централизованные секреты с повторным использованием и расширяемым хранилищем

Целевой репозиторий: `Flow-Steward/flow-steward-app`. Исходный `main`: `a78c2dd` (VERSION 0.9.7).

Результат: пользователь создаёт секрет один раз, выбирает его в подключениях и workflow
inputs, управляет значением и видит зависимости через «Реестр → Секреты». Внутренняя
граница позволяет позже подключить HashiCorp Vault.

Сохраняются глобальные `admin / operator / viewer`, общий контур доверия людей в установке
и существующие ограничения машинных полномочий. Проектные роли, персональные ACL и рабочая
интеграция Vault в объём не входят.

## Проверка основы

- Работа ведётся в публичном репозитории, не в `bmad-project`.
- ADR о секретах создаётся под следующим свободным номером (сейчас последний — 0048;
  перепроверить перед созданием). Решение из старого checkout — материал для нового ADR.
- Accepted ADR не переписываются задним числом; исключения оформляются явно.

## Правила продукта

| Вопрос | Решение |
| --- | --- |
| Project-секрет | Явно привязывается только к ресурсу того же проекта |
| Workspace-секрет | Явно привязывается к ресурсу этого workspace или его проекта |
| Между workspace/account | Запрещено |
| Одноимённые секреты | Независимые сущности; поиска и переопределения по имени нет |
| Привязка | По стабильному идентификатору, с серверной проверкой |
| Перенос ресурса | Проверить все привязки; при несовместимости отклонить с перечнем проблем |
| Замена значения | Следующее фактическое использование получает текущее значение |
| Старые workflow input references | Семантика и launch authority сохраняются; истории версий для подключений нет |
| Удаление | Блокируется текущими привязками; checkpoints и старые ревизии не считаются |
| Восстановление ревизии | Повторная проверка привязок; удалённый секрет — явная ошибка |
| Сохранённое значение | Write-only для всех человеческих ролей |

Доступность workspace-секрета означает возможность явной привязки, а не передачу всем.

## Порядок поставки

1. PR 1 — граница получения значений и локальный адаптер.
2. ADR об обновлениях до 1.0.
3. PR 2a — каталог, статические credentials подключений, переход данных.
4. PR 2b — workflow inputs и все пути изменения workflow.
5. PR 3 — общий UI реестра.

Между этапами не должно быть функции, у которой привязка работает, а проверка её
использования ещё нет. Каждый кодовый PR — focused tests и полный gate из финального коммита.

## PR 1. Граница получения значений и локальный адаптер

Без каталога, UI и новых таблиц.

1. Типизированный контракт чтения сохранённого секрета и рабочий локальный адаптер. Чтение
   ciphertext и расшифровка принадлежат адаптеру.
2. Подключить HTTP- и connector-пути сохранённых workflow inputs и статические credentials
   подключений.
3. Одна серверная точка сборки зависимости в `core/infrastructure/security/`. Явная подмена в
   тестах, deadline и контекст операции. Без глобального изменяемого реестра и кеша.
4. Структурно разделить статические credentials и `_oauth_*`: статические идут через контракт,
   OAuth остаётся на явно локальном пути, смешанные вызовы `include_internal=True` разделяются,
   refresh/запись/отзыв OAuth не меняются.
5. Inline-секреты расшифровываются локально по своей launch authority.
6. Проверки полномочий до обращения к адаптеру. Для workflow inputs — launch snapshot
   `_workflow_secret_ref_fingerprints` и доверенный account-контекст, без повторной проверки
   текущей роли в worker.
7. Статические credentials: настроенная ссылка обязана разрешиться; сохранённая `""` —
   значение; обязательность полей проверяет схема подключения.
8. Безопасные ошибки: запрет, отсутствие, повреждённое значение/расшифровка, временная
   недоступность. Через существующий `retry_policy.py` (`retryable`, классы отказов, deadline,
   факты внешнего эффекта). Запрет, отсутствие и ошибка расшифровки не повторяются.
9. Убрать `{exc}` из `connection_secret_resolution_failed` в `connector_connection.py`,
   `operation_targets.py`, `notifications/delivery.py`; код, безопасное сообщение и
   идентификаторы раздельно; проверить логирование и exception chaining.

Контекст адаптера: попытка workflow, один самостоятельный вызов операции, попытка доставки
уведомления. Контракт не требует DB-транзакции; ограничения будущего внешнего I/O перечислить
в PR.

Приёмка: локальные пути работают; подставной внешний адаптер разрешает сохранённые ссылки;
inline и дочерние workflow работают независимо от него; `_oauth_*` не попадает в адаптер;
неавторизованная ссылка отклоняется до чтения; ошибки безопасны и классифицированы.

## ADR об обновлениях до 1.0

Принимается до PR 2a, явно изменяет соответствующие ограничения ADR 0012.

- Поддерживаемая исходная схема и её проверка до обновления; порядок создания журнала и
  применения SQL до проверки нового baseline; блокировка параллельных обновлений, checksums,
  повторный запуск; поведение при неизвестной схеме и ошибке; соотношение fresh install,
  обновления и baseline 1.0.
- SQL и существующий runner с доработкой оркестрации; без per-migration Python, скрытого
  reconcile и ручного `ALTER`.
- Стадии: read-only preflight → транзакционный SQL-переход → идемпотентная Python-фаза
  (та же функция проекции и fingerprint, что в runtime; подтверждения, аудит и отметка
  завершения атомарно) → финальная проверка готовности.
- **Восстановление только вперёд.** После коммита SQL-стадии ошибка стадий 3–4 исправляется
  повторным запуском той же версии. Откат на предыдущую версию — только восстановлением
  бэкапа. Предыдущая версия обязана отказаться стартовать на перенесённой БД (проверка
  схемы при запуске), а не работать на ней.
- **Остановка старых процессов.** До SQL-стадии все процессы предыдущей версии (app, workers,
  scheduler, на Scalable — каждый сервис) остановлены. Preflight проверяет это и
  останавливает обновление, а не полагается только на `--maintenance-confirmed`.
- До завершения обязательных стадий новая версия не обслуживает обычные исполнения.
  Проверить остановку и повторный запуск между стадиями.

## PR 2a. Каталог, статические credentials подключений, переход данных

- Инвентаризация в PR: `владелец → хранилище значения → хранилище ссылки → потребители →
  переводится / остаётся`. Перечислить непереведённые пути.
- Реляционные привязки с FK на секрет и `ON DELETE RESTRICT` — источник истины. JSON-проекции
  не редактируются независимо; изменение потребителя и привязки атомарно.
- Scope `secrets:bind` и `secrets:write`: в `scope_granted` требуется точное наличие, проверка
  до `admin:all` и wildcard. Отказ для каждой формы: `admin:all`, `*:*`, `secrets:*`, `*:bind`,
  `*:write`. Существующие токены новых полномочий не получают; выпуск и делегирование не
  превращают wildcard в поимённое разрешение.
- Подтверждение использования привязок для конкретного fingerprint исполняемой конфигурации.
  Подтверждают admin и operator только через доверенный контекст интерактивной сессии;
  машинные токены, MCP и LLM-authoring — нет. Обычное сохранение и «Применить» в AI Builder
  подтверждением не являются. Runtime проверяет совпадение исполняемой конфигурации с
  подтверждённой.
- Каноническая исполняемая проекция: привязки и передача секретных входов; шаги, код,
  шаблоны, mappings, условия, маршрутизация; назначение и allowlist; release ID и digest
  расширения. Названия, описания и координаты canvas исключены.
- Allowlist назначения — часть подтверждаемой конфигурации: схема, host, эффективный port,
  необязательный префикс пути с границами сегментов. Типы правил `exact_host` и `subdomains`
  (базовый домен — отдельным флагом, границы DNS-меток, запрет публичных суффиксов). Без glob
  и regex. Динамический URL без allowlist подтвердить нельзя. `follow_redirects=False` —
  обязательный инвариант.
- **Public Suffix List — закреплённый снимок.** Сетевое обновление списка выключено
  (например, `tldextract` по умолчанию скачивает список — запретить). Снимок закреплён в
  репозитории или пакете с указанием версии; зависимость проходит `pip-audit` и проверку
  лицензии; обновление снимка — явный коммит с тестами нормализации.
- Переход данных: SQL переносит строки и ciphertext без расшифровки; Python-фаза создаёт
  первоначальные подтверждения от системного актора переноса с аудитом; без дублей при
  повторе; не подтверждает изменённые после перехода конфигурации. Динамические назначения
  без ограничений — read-only preflight и `--secret-destinations-file` (версия формата,
  account, потребитель, шаг/вход, fingerprint исходной конфигурации, правила; без значений;
  неизвестные поля, дубли и расхождения — ошибка). При неуспешном preflight SQL не начинается.
- Минимальные действия UI в этом же PR: «Подтвердить использование секретов» на карточке
  подключения и «Подтвердить релиз для выбранных подключений» (прежний/новый release и digest,
  список, изменения; конфликт без частичного подтверждения при изменении набора).
- Неподтверждённая конфигурация видна в карточке, списке и поверхности «требует внимания».
  Расписания и триггеры получают `secret_configuration_unapproved`, `retryable=false`.
- Cleanup: `cleanup_project_connection_owned_data`, `delete_connection_secret_refs` и вызывающие
  его connection/OAuth cleanup не уничтожают общий секрет.
- Аудит: создание, замена значения, метаданные, привязка, отвязка, удаление, подтверждение.

## PR 2b. Workflow inputs и пути изменения workflow

- Модель каталога и подтверждения для workflow inputs, import/export, clone, restore, AI Builder.
- Обычные payload сохранения и LLM-изменения отклоняют поля привязок и подтверждений.
- Дочерний workflow, получающий каталоговый секрет, имеет собственное подтверждение; проверка
  на каждом уровне вызова.
- Read-only инвентаризация динамических HTTP-назначений на стендах и в каталоге шаблонов до
  начала; количество и непроверенные окружения — в PR.
- Негативные сценарии: машина меняет URL HTTP-шага; LLM меняет код/mappings/маршрутизацию;
  человек нажимает «Применить»; import/restore восстанавливает привязку напрямую; машинный запуск
  подставляет назначение; машина меняет URL в дочернем B при неизменном A.

## PR 3. Реестр секретов и выбор на месте

Список и карточка, создание, замена значения, метаданные, удаление, выбор и создание на месте
в credentials подключений и workflow secret inputs, переход к карточке, понятные ошибки,
отдельный одноразовый ввод при запуске. Browser-проверки сценариев. Без неработающих настроек
Vault.

## Проверки

Все gates — через `lint.sh` внутри `fs-audit`. Compose-проект выбирается по инвентаризации:
подходящий audit-образ, отсутствие чужого gate под этим именем, ресурсы. Не использовать имя
стенда и не занимать проект другого запуска: cleanup gate удаляет его audit-сервисы. В каждом PR
— исходный и финальный SHA, команды, результаты, непроверенные условия.
