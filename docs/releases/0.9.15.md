## Flow Steward 0.9.15

### Composite extension actions

- An extension action can now be implemented by a workflow bundled in the same extension (`handler.mode: workflow`, [ADR 0065](https://github.com/Flow-Steward/flow-steward-app/blob/v0.9.15/docs/architecture/adr/0065-composite-extension-actions.md)). In a workflow the step is still an action of its extension. Under the hood it runs the bundled workflow as a child run.
- In the builder, choosing such an action shows the extension, the action, one connection picker per connection slot, and the action's input and output mappings. A slot with exactly one fitting connection is filled in automatically. Slots are labelled by their extension.
- The implementing workflow is hidden. It never appears in the catalog or the Invoke picker, cannot be linked to a project, and runs only as the child of its action.
- An extension update that would break a workflow calling one of its composite actions is refused and names the calling step. Export lists the action's extension as a dependency, and import points the step at the installs and connections of the importing account.
- The extension authoring playbook has a new Composite Actions section.

### Run page

- Tool steps are named "Extension action", "MCP tool" or "System tool" instead of "connector step" and "Tool Action". A summary line reads, for example, "Extension action 'X' completed".
- The step inspector shows the extension's display name. Earlier runs get it as well.
- A finished step that ran another workflow links to that run. The run of a composite action is listed in Jobs as "workflow name · extension name" and points back to the run that started it.

### Database size

- Workflow runs no longer keep every intermediate checkpoint. Each run thread keeps only its latest checkpoint, which is the only one Flow Steward reads. Previously, a long agent run stored its whole message history again at every step, and checkpoint tables could grow to many gigabytes.
- Daily retention also compacts finished jobs, one hour after they finish, down to their latest checkpoint.

### Backup, maintenance and upgrade

- `backup create` and `backup restore` no longer stop after a fixed time limit. Large databases are dumped and restored to completion. `pg_dump` still gives up if it waits more than 5 minutes for a table lock.
- A failed `backup create` no longer blocks `maintenance disable`, `doctor` or readiness. `status` and `doctor` show the last failed backup as a warning until a later backup succeeds.
- When the database preflight blocks `database upgrade`, the command reports `database_upgrade_blocked` (exit code 4) with each blocking issue, the connected sessions and the next step, instead of `internal_error`.
- On Scalable, the CLI prints the operation log path on the host instead of the path inside the container.
- On Scalable, `database upgrade --maintenance-confirmed --confirm`, run while maintenance is enabled, stops the previous release's app, worker, control-plane, MCP and extension-installer services before it migrates. Postgres, RabbitMQ and storage keep running. `./install.sh` or a repeated `release upgrade` starts the new release.

### Security

- Error responses no longer include raw exception text from databases, libraries or the operating system. Details go to the server log, and the response carries a fixed message and a code.
- Log lines that can quote a credential are redacted: email delivery errors, notification failures, invalid tool definitions and cutover preflight details.
- Extension files are resolved strictly inside their extension bundle wherever they are read, scanned, compiled or served.
- Remote extension runtime URLs, OAuth callback redirects and report download cookies only use values that the host has validated. Outbound TLS requires TLS 1.2 or newer.
- Three regular expressions with quadratic worst cases now run in linear time: credential redaction, prompt-injection markers and browser asset paths.
- The dot-path setters in the platform UI kit ignore `__proto__`, `constructor` and `prototype`.
- Clone state files are created owner-only. The clone plan fingerprints the database identity with PBKDF2 instead of a plain SHA-256.

### Dependencies

- LangGraph 1.2.14 with langchain-core 1.4.9, virtualenv 21.14.13, and minimatch 11.0.7 for the frontend lint toolchain.

### Upgrade notes

This release adds no database migration.

Compaction removes old checkpoint rows, but PostgreSQL does not return their disk space to the operating system on its own. On an installation whose checkpoint tables have grown large, wait for the first daily retention pass after the upgrade. Then run `VACUUM FULL` on `checkpoints`, `checkpoint_blobs` and `checkpoint_writes` during a maintenance window. `VACUUM FULL` locks each table while it runs.
