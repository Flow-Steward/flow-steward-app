## Flow Steward 0.9.18

### Extensions

- A read-only workflow that an extension provides can now use a connection of the project. The workflow declares the connections it needs as connection slots (`settings.connection_slots`, with a label), and its connector steps read a slot instead of a connection id. Before, such a step failed with `connection_resolution_failed: explicit connection binding is required`, because nobody could set a connection on a step the project cannot edit.
- The Overview of such a workflow shows a Connections card: "This workflow needs: <label>" with a selector of the project's connections of the right extension and type, for each linked project. With exactly one usable connection, it is chosen automatically. Administrators can also read and set the choice through `GET` and `PUT /api/projects/{project_id}/workflows/{workflow_id}/connection-slots`.
- A workflow whose connection is missing, or that has several to choose from and no choice, is not ready in that project. A run from the UI, a webhook, a schedule, a provider trigger, a restart or an Invoke step that starts it is refused before it starts with HTTP 409 and the code `workflow.connection_slots.not_ready`, and the message says what to do. A connection that was chosen and later disabled or failing is never replaced by another one without asking.
- Each run keeps the connection it started with. A child workflow of the same extension started by an Invoke uses the parent run's connection for a slot of the same name.
- An extension update that adds a connection slot, or changes the connection types a slot accepts, is activated only when every project that links the workflow has a usable connection for it; otherwise the update is refused with the workflow, the project and the reason, like a changed hook. A project can choose for the new release first. Removing a slot drops the choices made for it.
- Uninstalling an extension or deleting a connection removes the choices that used it. Exported workflows never carry connection ids.
- A bundle is refused when a workflow step reads a connection slot the workflow does not declare, keeps a fixed connection id next to its slot, or declares a slot of an extension it does not depend on. A bundle that declares connection slots needs `runtime.compatibility.platform_min: 1.8.0`.
- An extension callback can now verify a provider that signs the raw request body with a connection secret: `auth.type: raw_body_hmac_sha256` names the signature header, an optional exact prefix, the encoding (`hex` or strict padded `base64`) and the secret field of the owning connection type. An optional GET subscription handshake either echoes the challenge after checking the registration's verify token, or answers with a JSON field holding the HMAC of the challenge under the same connection secret, encoding and prefix. A request with a bad signature is refused with 401, a bad handshake with 403; neither reaches the extension, and a handshake never starts a workflow. The existing `hub_signature` preset now runs through the same verification and keeps its behaviour. Callback access-log records no longer contain the capability path segment or any query value. A bundle that declares the new type needs `runtime.compatibility.platform_min: 1.9.0`. See ADR 0072.
- The extension host contract is now 1.9.0 (1.8.0 for connection slots, 1.9.0 for raw-body signed callbacks; the wire contract stays `extension_host_v2`).
- A table on an extension page can link its cells, or whole rows, without markdown: a grid column of `type: link` opens another page of the same extension with `p.<name>` parameters filled from the row (`link: {page: run_detail, params: {run_id: "{row.run_id}"}}`), or an in-app path the row holds (`link: {path_field: job_path}`); `row_link` makes a click anywhere in the row open the same kind of target. Only same-app links are possible, values are URL-encoded, and the link opens in place without reloading the app.
- A table on an extension page can declare filters above it: a select with fixed options or options from an ordinary query, or a text box. Each filter is bound to a `p.<name>` page parameter; changing it updates the address, returns the table to its first page and loads the page's data again.
- The compiler refuses a grid link to an unknown page, a link that reads a row field the grid does not declare (a column key or `row_fields`), a malformed parameter, a filter whose options come from an unknown query or a query with a connection, and two filters for the same parameter.
- Importing an extension whose OAuth provider descriptor inherits its contract no longer loses it: a runtime value of null no longer replaces the executable OAuth settings, and the provider fingerprints stored for an installed release are kept through updates.
- The extensions list and extension icons load faster: an extension is read with one lookup instead of reading every manifest, an icon no longer builds the full extension detail, and the list does not compile again a bundle that is already installed (a folder that two extension ids would share is still refused).
- A callback that the provider is set up for by hand (`callback_setup.setup_mode: manual`) can be created from the extension page for the connection chosen on that page. The one-time callback URL and verify token are shown once to the manager who created them and are never stored in the browser; they are discarded when the account, project, installation, connection or permission changes. Callback actions run only for a resolved owner of the registration and refuse when it cannot be resolved.
- An extension can now change its own connection's configuration atomically with the host mutation `project_connection_config_compare_and_set`: it states what it expects (`absent`, `equals` or `absent_or_equals` for each path) and what to set, and the host applies it only if the expectation still holds when the row is locked. Two concurrent first writes give one winner; the other gets `host_mutation_precondition_failed`. The comparison and the change happen in the database on the stored JSON, so untouched values keep their exact form, and paths under `oauth` are refused. The mutation needs the grant of the same name and `platform_min: 1.9.0`. See ADR 0073.
- An OAuth connection whose identity check fails after a reconnect or a retry stays bound to the account it already had; a different account never becomes active under the same connection.
- An installed extension finds its Python dependencies by the version recorded for the installed release, and an imported extension keeps its compiled UI in the runtime descriptor, so OAuth can check that the return page owns the connect intent.
- Enabling an extension whose bundle was updated in place (a scanned bundle) now accepts the browser code approval shown for the installed release, and only that exact approval: the publication must have the same account, project, installation, previous release and byte-identical bundle files, and the same browser surface. Any other change is refused as before; a bundle that lost `extension.yaml` is reported as broken instead of asking for an approval.

### Workflows

- A Wait step can now wait for an event instead of a time: **Until an event** names the extension that reports it, the event types (for example `run_completed`, `run_failed`), a correlation key (usually the id the previous step returned, such as `state.crawl.run_id`) and a required timeout. The run is parked as `awaiting_event` without holding a worker, and the job shows "Waiting for … (key …) since …, times out at …". The event's payload is the step's result and can be mapped to state; at the timeout the step fails with `workflow.wait.event_timed_out`, and its error policy decides (fail, continue, the error edge, or retry to wait again). Cancel works as for any waiting run. See ADR 0071.
- An extension resumes such a run by returning `resume_waits: [{correlation_key, event_type, payload}]` in a successful action or callback response. Only that extension, for the run's own account and project, can resume it; the key must match exactly and the type must be one the step lists. Each event resumes one run once, a repeated delivery is ignored, an event that arrives before the run reaches its Wait is kept for it, and payloads are limited to 64 KiB and redacted. Undelivered events are deleted after 7 days.
- A waiting run says what it waits for: "Waiting for … from <extension> (key …) since …, times out at …", and the job API's `workflow_wait` now carries `source`, `event_types`, `correlation_key`, `timeout_ms` and `started_at` besides the deadline. After the event arrives, the Wait step shows which event woke it, when, and its payload (redacted like any step result); a timer Wait shows the time it waited until. Before, both showed an empty step.
- When an Invoked child workflow fails or is cancelled, the parent's Invoke step now shows as failed with the child's own reason: "Child workflow 'x' finished with status 'failed' at step 'y': <the child's error>". The step's result carries `child_status`, `child_job_id`, `child_error_code`, `child_error_message` and `child_error_step_id`; the step's error route can read them (`message.step.<step_id>.artifacts.child_error_message`), and the Invoke's `output_mapping` may map them to state (`child_error_message: state.scrape_error`). An unhandled failure carries the same reason to the parent job. A step whose failure an error route or Continue took is now listed as failed, not completed.
- Runs of one workflow can be told apart without opening their inputs. A schedule now has a **Name** (required in the schedule form; `name` in `POST` and `PUT /api/projects/{project_id}/scheduled-jobs`), shown in the schedule list. A workflow can declare a **Run title** in its settings, a template over its inputs such as `{{ inputs.site_url }}` (`settings.run_title`). Each new job is titled with the schedule's name or the incoming webhook's description, followed by the rendered run title: `Supplier A · https://a.example`. The title shows in Jobs (and Jobs search finds it), as the heading of the job page, on an Invoke step's link to its child run, in the schedule run history and in monitoring (`run_title` on job rows). A secret input is never rendered, and saving refuses a template that reads one, an undeclared input or anything other than `inputs.<name>`.

### Extension pages

- An extension page loads the data of all its components at the same time instead of one after another, and each component shows its data as soon as it arrives.
- Coming back to an extension page (Back, a link, another page of the extension) shows the data it last showed at once and refreshes it in the background.
- A link to a page of this app inside an extension page's text opens in place, without a new tab and without reloading the app; links to other sites still open in a new tab.
- A query process that has finished is noticed at once; the host used to wait up to 50 ms more for every query. Each query result now carries `host_timings_ms` (the milliseconds of each host step and the total) and `process_ms` (the extension process from start to exit), to find what makes a page slow.
- Pages that read lists from the server (Overview, extensions, projects, jobs, MCP, monitoring, Trash, guardrails) no longer block other requests while they read the database, so a slow list no longer makes the rest of the app, and `/health/live`, wait.

### Lists and administration

- Workflows show 25 rows per page by default, with the shared page controls, a page-size choice and page reset when filters change.
- Names in Jobs, Projects and Workspaces use the same green detail links as the other registries, including keyboard navigation and opening in a new tab.
- Internal extension headers show a short introduction of at most two lines. The full descriptions remain in About and the extension catalog.
- The Test Run dialog gives file uploads a visible button and outlined area, separates the confirmation checkbox from its text, and gives summaries and paragraph/JSON inputs their multiline height.
- Job Model usage shows readable agent and processing names instead of extension installation identifiers. Recorded names are preserved, technical IDs remain available on hover, and usage totals are unchanged.
- Lists remember their search and filters in this browser, for each account, user and list. A link that carries filters still wins, Reset clears the remembered choice, and Back works as before.
- Administrators see a banner above the header when a newer Flow Steward release is published, with the installed and the new version and a link to the release notes. The check reads public release metadata at most once an hour (every 5 minutes after a failure) through `GET /api/system/core-updates`, which only administrators can call. Nothing is installed from the browser; upgrades stay with `flow-steward release upgrade`.

### Fixes

- The Result panel of a job now offers each final file of the run (for example a scraper's CSV and JSON Lines result) as a file you can open or download. Before, it only listed the file's id, size and checksum, and the download link existed only inside the step that made the file.
- Readiness no longer reports "Choose a connection for this extension action" for a step that reads its connection from a declared slot, so a composite action or a slot workflow is not marked invalid for a connection it receives when it runs.
- Secret redaction no longer mistakes translation keys such as `react.jobs.step_wait_event_received` for tokens, so step summaries are translated again; real tokens after a short dotted prefix are still hidden. Event times in a Wait step's result are ISO 8601 UTC.
- The schedule form's **Name** field is labelled only "Name"; its help text is linked to the field instead of being part of the label.
- `flow-steward --version` works on Compact installations and reports the version of the selected management CLI image.
- The web app imports its validation library only through the wrapper that runs it without generated code, so pages keep working under the Content Security Policy.

### Known limitations

- The Facebook, Instagram, LinkedIn and X extensions ship separately from Core. Their checks against this release confirm host compatibility using local test services and test stands only; connecting real accounts and publishing through them was not part of this release's checks.
- A source installation of the Compact profile that started as an official installation keeps recording itself as official and keeps the official management CLI and MCP image selected; `flow-steward release info` then refuses until `FS_INSTALL_MODE=source` is set and those selections are cleared. `doctor` does not report it yet.
- After an update, `doctor` can warn (`release_retention`) about an older retained application image whose exclusive ownership cannot be proved; it keeps the image and does not delete it.
- The web app build reports that the agent skill package archive chunk is larger than 700 kB, and Vite deprecation notices for its config loader and `inlineDynamicImports`. The build succeeds with these warnings.

### Quality gate (contributors)

- The hosted release gate runs Tier 3 on four parallel runners (backend, backend-frontend contracts, frontend, external checks) and then reads all of their results in one cumulative check; Sonar runs beside that check instead of after it.
- A release run imports the check results of the latest runs of its branch and of main. A check whose inputs a commit did not change is not run again, so a retry after a small fix no longer repeats the whole gate.
- The backend and frontend suites run only the tests a change reaches since the last result of the same suite: the backend records which files each test module executes and reads, the frontend uses `vitest related`. Tests that failed last time run again. A change to dependencies, the database schema, test configuration or the gate itself runs the whole suite, and a weekly run on main (and the `release-full` mode) runs every suite whole. See ADR 0070.
- The backend suite warms pytest's assertion-rewrite cache before its parallel workers start; collecting the suite takes about half as long.
- A daily job keeps the repository's Actions cache under 7 GiB and deletes release image archives older than three days.

### Upgrade notes

This release adds the table `workflow_connection_slot_choices` with migration
`20261114090000_workflow_connection_slot_choices.sql`, and the table
`workflow_wait_events` with two partial indexes on `jobs` with migration
`20261114160000_workflow_wait_events.sql`. They only create tables and indexes;
no existing data changes.
Migration `20261114150000_scheduled_job_name.sql` adds the column
`scheduled_jobs.name` (empty for existing schedules); no other data changes.
Migration `20261114190000_raw_body_callback_auth.sql` lets the
`extension_callback_registrations.auth_type` check accept
`raw_body_hmac_sha256`; existing registrations do not change.
Apply the migration during the upgrade as described in the
[upgrade guide](https://github.com/Flow-Steward/flow-steward-app/blob/v0.9.18/docs/GUIDE.md#maintenance-and-release-upgrade).
