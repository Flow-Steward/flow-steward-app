## Flow Steward 0.9.19

### Fixes

- ChatGPT can connect to Flow Steward again. Its sign-in stopped on the "Connection stopped" page with "The app's identity document is not accepted" (`invalid_client_metadata`). ChatGPT's identity document now names `private_key_jwt` as its preferred way to sign token requests while also listing `none` among the ways it supports; Flow Steward only looked at the preference and refused. It now reads the list of supported ways, so ChatGPT signs in as a public client with PKCE, the only kind Flow Steward accepts. Claude was not affected.
- The app name on the "Allow … to access Flow Steward?" page is visible again in a browser that has not chosen a Flow Steward theme yet, such as the one an AI app opens on a phone. The page used light colours but told the browser to use dark defaults, so plain text such as the app name was drawn white on white.
- A clean installation with the bundled file storage (SeaweedFS) no longer fails at "Verify selected file storage" with `storage_verification_failed` (exit code 8). The application creates its artifact bucket when it starts, and the installer could create the same bucket a moment later: its check saw no bucket, its create was answered with `BucketAlreadyExists`, and the installation stopped although the bucket was ready, so `./install.sh` had to be run a second time. The installer and the upgrade storage probe now take "already exists" as that race, wait a few seconds at most for the bucket to become visible, and then still write and delete a real test object. Access, credential and endpoint errors still fail the step at once.
- Flow Steward MCP tools now answer with a real JSON object. Every tool published its output as `{result: string}`, so an AI app that reads the structured result (as ChatGPT does) got the answer as JSON text inside a string, and `job_status` returned no structured result at all. All 74 tools now publish the `{ok, tool, data, meta}` envelope as their output schema and return it as an object; the text part still carries the same JSON, and errors are unchanged.
- Flow Steward MCP tools now tell an AI app which of them only read and which change things. No tool carried MCP annotations, so an app such as claude.ai treated every tool as an unknown write and could not show a read as safe. All 74 tools now publish `readOnlyHint`, `destructiveHint`, `idempotentHint` and `openWorldHint`: 47 tools only read, starting a run and deciding an approval are marked as destructive changes that reach outside Flow Steward, and creating something new is marked as additive. The hints only describe a tool; the API still checks role, scope and policy on every call.
- Links in MCP answers open from another app. `workflow_draft_save` returned the editor link as a bare path (`/registry/workflows/…/builder`), and report links came back as `/jobs/…`, so the AI app had to guess the address. Product page links (the editor, job page and connection setup links, and report `deep_links`) now carry the installation's public address (`FS_PUBLIC_BASE_URL`). Other values, such as a workflow default or report data, API paths and installations without a public address are unchanged.
- Validating a workflow draft that names a missing or hidden agent, skill or child workflow now also checks the draft's own Interface. Before, validation reported only the missing dependency, and saving then refused an Interface field (for example an input of type `date`) that validation had not mentioned.
- An agent without a model of its own now gets the readiness warning `agent.model_unset`, shown by `agent_validate`, `workflow_validate` and the workflow editor. Before, an agent could be enabled and its workflow showed as ready, and the first run failed with `model_unavailable`. It stays a warning, because a project default model or a per-agent override can still supply the model.
- Removing the last skill from an enabled agent with `agent_skill_unassign` (MCP) or `DELETE /api/agents/{agent_id}/skills/{skill_id}` is now refused with a validation error that says why and what to do: assign another skill first, or disable the agent. Before, the skill was removed silently and the agent stayed enabled although it could no longer run, the state enabling an agent already refuses. A disabled agent can still lose its last skill.
- Workflow search for AI assistants (`capability_search`, `workflow_examples_search`) uses the workflow knowledge index again instead of running on its keyword fallback forever. The background sync refreshed only the account-wide knowledge, because it took its scopes from registry changes and a workflow change names no project, while every search is made inside a project; the answer therefore always said `freshness: empty` / `missing_scope_digest`, and among similarly named workflows the newest could drop out of the top results. Each sync request now also refreshes the knowledge of every project (the 100 newest), so a project's search is fresh within one sync interval (5 minutes by default) of a change. A running server also picks up the newer index without a restart: before, it kept comparing against the index version it had remembered and stayed on the keyword fallback.
- An AI assistant no longer offers to send a workflow input that has a configured default. `workflow_contract` listed such an input in `input_schema`, and `workflow_trigger` then refused the value with `workflow.input.override_forbidden`. `input_schema` now lists only the inputs a caller may send; an input with a configured default stays visible in `expected_inputs` with `caller_may_supply: false`, and both tool descriptions say it is fixed.
- `job_approval_decide` now says that rejecting needs a non-empty `comment`, and what `action: "abort"` does (it ends the run as cancelled and needs no comment). Before, the tool showed `comment` as optional and refused a reject without one.
- The agent and skill authoring schemas list the categories the server accepts (`ai`, `cms`, `crm`, … `support`) instead of showing `category` as free text, and they name the MCP tool next to each API route (for example `agent_create` next to `POST /api/agents`).
- Refusals now name the real cause: converting a group to a child workflow says which workflow output is not written on every successful path (instead of "may come from moved message history"); importing a workflow file with a new hook on a production installation says a hook needs a Development environment (instead of "invalid topology"); and validating a draft that calls a disabled child workflow in the same project says the child is disabled and how to enable it (instead of "Reference is not available in the selected account/project scope"). The group examples in the workflow authoring schema now say they cannot be converted to a child workflow as they are.
- Dispatching a project notification that reaches no route now says why: the answer carries `routes_matched: 0`, a `reason` (`no_enabled_route` or `no_route_matched_event`) and a `message` naming what to configure, instead of an empty list.
- The workflow authoring schema reports the installation mode (`installation_mode`) and no longer offers hook examples on a production installation, where a new hook declaration is refused.
- A token that lacks a scope is now told which scopes the request accepts ("Missing required token scope (needs one of: …)").
- A run that reaches a successful end without writing a required output (for example a report the reviewer rejected) no longer fails without a reason. It still fails, because the workflow's Interface requires that output, but the job error, the incident, the job status and the run report now say which output was missing and which end step the run reached, instead of "No explicit root cause recorded." and "ended (failed) without a report". Checking or saving such a workflow now also shows a warning: "Required output '…' is not written on every path that reaches a successful end (e.g. via … → …)".
- Activity, project summary and project stats reports now count runs that finished just before the report was generated. They read the dashboard summary, which is refreshed every few minutes, so a report made right after a run left that run out while its window ended "now". Runs the summary has not picked up yet are now read directly, the report says what time its data is from ("Data as of"), and cancelled runs are counted separately instead of being left out silently. The three report types show the same numbers by design; only their text differs, and the AI tool description now says so.
