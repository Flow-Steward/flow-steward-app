## Flow Steward 0.9.22

### Security

These come from a security audit. None was rated critical.

- **HTTP request step:** a request that uses a secret from the secret catalog and
  also sets its own `Host` header is now refused with
  `secret_destination_not_allowed`, and nothing is sent. Before, a custom `Host`
  header could deliver the secret to a server other than the approved one.
  Workflows that set `Host` together with a catalog secret need the header
  removed.
- **Approved destinations:** a request's URL is now checked against a secret's
  approved destinations with the same parser that sends the request. A URL whose
  path cannot be read is refused instead of failing with an error.
- **Workflow inputs:** an object or array input sent as a JSON string is now also
  checked after it is decoded. If the decoded value contains an internal secret
  reference, the run, or a step test run, is refused. Ordinary JSON inputs are
  accepted as before.
- **AI agents, Claude plugin:** the downloaded plugin no longer contains your
  access token, only the MCP address. Claude asks for the token when the plugin
  is installed, and the AI agents page has a step to copy it. A plugin downloaded
  from an earlier release still holds the token; revoke that token.
- **MCP connectors:** when a connector's header uses a catalog secret, changing
  the connector's URL, its headers or its OAuth setting now needs the permission
  to use that secret, the same as changing the secret itself.
- **Secret approvals:** a token limited to certain workflows now sees and approves
  secret requests only for those workflows. A caller limited to certain
  workspaces can no longer read or approve connection approvals of projects in
  other workspaces.
- **Workflow export:** an exported workflow bundle no longer includes project
  guardrails, or the extensions they depend on, from projects or workspaces the
  caller is not allowed to see. This applies to the export in the admin UI, the
  MCP export tool and the examples the authoring catalog shows.
- **PII redaction:** when two detections overlap, such as a phone number inside
  an email address, the whole span is now replaced once. Before, the
  replacements were applied one after the other and could garble the text.
- The injection, PII and secret scanners were rewritten so that crafted input can
  no longer make them slow. They find the same things as before.

### Fixes

- Compact `./install.sh` update: the installer now waits, for up to three
  minutes, for the recreated `compact-runtime` to finish starting before it
  reports readiness. Before, an update could fail with "Core readiness blockers
  remain: Compact runtime" while the runtime was still starting, and a rerun a
  minute later succeeded. If the wait runs out, the log and the error name each
  failing check and its reason.
- `./install.sh`: rerunning an update that stopped at readiness now records the
  new release as installed and the previous one as the release it replaced.
  Before, the rerun left the old release recorded as current, and the replaced
  release lost its protection from image cleanup.

#### Messages during upgrades

These came out of testing upgrades from 0.9.12 and 0.9.15 to 0.9.20 and 0.9.21 on
Compact. None of them stopped an upgrade, but each one made it harder to tell
what was going on.

- Compact: `database upgrade` now says that it stops `compact-runtime` and that the
  runtime stays stopped until the release upgrade starts the new release. Before,
  it stopped the runtime without saying so.
- Log paths are now host paths inside the installation folder.
  - Compact `database upgrade` used to print `Log: /app/logs/cli/...`. That path
    was inside a one-shot container and was deleted when the container exited.
    The log is now kept in `.flow-steward/logs/cli` and reported there.
  - Paths inside the Compact CLI container's state directory
    (`/run/flow-steward-install-state/...`), such as the log of a failed
    `release upgrade`, are now reported under the installation's `.flow-steward`
    directory.
- `release info` now shows an unfinished upgrade. It reports `upgrade_pending`,
  the release that is waiting to be applied, and the command that resumes the
  upgrade. Before, it showed only the installed release.
- Compact: `status` now explains a stopped runtime. Before, while an upgrade was
  stuck after `database upgrade`, it said only `health probe failed (gaierror)`.
  Now it names the unfinished upgrade and the `release upgrade` command that
  completes it. If no upgrade is pending, it says that `compact-runtime` is not
  running and gives the command that starts it.
- `"still working"` lines no longer appear after a step has finished. A step's
  last heartbeat could arrive after its ✓ line, put the step back on the list of
  running steps, and keep the notes coming until the command ended.
- The summary line of `doctor` now suggests
  `./flow-steward doctor --fix <ids> --confirm`. It used to leave out `--confirm`,
  so the pasted command changed nothing when run without a terminal. The JSON
  `fix_command` now includes `--confirm` too.
- `./install.sh` and `release upgrade` now make installation state readable by its
  owner only, including state that an older release left readable by others.
  0.9.15 on Docker Desktop left `.flow-steward/.docker-desktop-mount-probe` at
  0644. `doctor`'s `secrets_modes` check failed on it until
  `doctor --fix secrets_modes --confirm` was run.
- `database preflight` now exits with code 4 when the upgrade is blocked. It lists
  each blocking issue the same way `database upgrade` does. Before, it listed the
  issues and exited 0, so `database preflight && database upgrade` went on to an
  upgrade that was then refused.
