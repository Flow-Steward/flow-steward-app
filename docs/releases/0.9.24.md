## Flow Steward 0.9.24

### Operators: sections, forms and a review page

Administrators can now give people who only run and check work a focused
workspace (ADR 0075).

- **Sections.** In Workflow Settings, the tab *For operators* turns a published
  workflow into a section of the operator menu. You choose:
  - which inputs the form shows, and with which widget;
  - which results and list columns operators see;
  - the typed filters of the list.

  The fields and their types come from the workflow contract. Conditions show a
  field only when another has a given value. A repeater collects rows of
  sub-fields.
- **Forms.** Operators start a run from the form:
  - files are uploaded in the form, several files in one list-of-files input;
  - on a phone the camera can take a photo straight into a file field.
- **Review.** An Approval step can carry typed review fields.
  - The person checking sees the original document beside the fields, corrects
    values, and approves or rejects with a reason.
  - A queue moves to the next item (J/K).
  - The decided values become step outputs.
- **Job view.** One layout for every job of a section. It shows the run's inputs,
  results and decided review, plus *Send again*.
- **Document previews.** PDF, spreadsheet and DOCX files are drawn in the page,
  for job files and for the review original (ADR 0080).
- **Phones.** A menu button opens a full-width navigation drawer.

### Roles and permissions

- **Clear role split (ADR 0076).**
  - Administrators configure.
  - Operators run and review.
  - Viewers read.
- **Permission keys.** Each person's permission keys come from a stored role
  catalogue and decide menus, pages and buttons. Every API route and MCP tool names
  the permission it needs.
- **One system role per user** in the user form, the CLI and the API.
- **AI agents.**
  - An AI agent can be connected with one button *as my role*.
  - Cloud clients (OAuth) connect with the person's role.
  - The owner gets an email seven days before an agent connection ends.

### Sign-in and accounts

- **Authenticator requirements.** An administrator can require an authenticator
  app per user, with recovery codes. Password history and the 12-character minimum
  from 0.9.23 stay in force.
- **Personal data guard.** Document and receipt numbers are no longer mistaken for
  phone numbers and pseudonymized. A phone now needs a `+` country code or
  separators.

### Notifications and system email

- **Explicit sender for system email.** A platform administrator chooses the one
  connection that sends password reset, welcome and email change messages, in
  *Settings → Email* (ADR 0081).
  - The choice is pinned to that connection, install and type, and only a platform
    administrator can change the connection's settings, secrets or sign-in.
  - Any such change, including disabling and re-enabling the connection, needs a
    new confirmation; there is no silent fallback to another sender.
  - Existing installations keep the sender they used, pinned once on upgrade.
- **Mixed notification providers.** One extension can deliver both to people
  (email) and to channels, decided per connection type.
  - Routes of such providers name their connection.
  - A channel bound to its connection, such as a webhook URL, takes no channel in
    the route.
- **System message bodies are never logged.** That covers the reset and email
  change links in them, in every log level.

### Extensions

- **Crash-safe connection polls.** An extension can poll an external system per
  connection in the background (`background.kind: connection_poll`) and start
  workflows from what it finds.
  - Each new item starts a bound workflow exactly once, across crashes, restarts
    and concurrent workers.
  - Polling is off for a connection until switched on.
- **Credentials on every call path.** Notification deliveries get the connection's
  refreshed OAuth token and an `idempotency_key`; the event carries `run_url`.
- **Idempotency key for direct actions.** An effectful action called from a page or
  the API passes the request's idempotency key to the extension in
  `runtime_context.idempotency_key`.
- **Shared app credentials.** A connection type can take its application
  credentials (`credentials_from`) from the extension's OAuth configuration, so an
  organisation app is entered once for all its connections.
- **OAuth survives updates.** An extension update that does not change sign-in
  keeps its OAuth connections working at once. An update that does change sign-in
  says why the connections need attention.
- **Core-owned keys are not schema-checked.** Core's own keys in a connection's
  settings are no longer judged against the extension's schema.
- **Author documentation.** New sections in the extension authoring playbook:
  background connection polls, notification providers and `credentials_from`.

### Agents and routing

- **One model call per agent without tools.** An agent without tools answers in
  its response schema in one model call.
- **Reasoning depth.** An agent can set GPT-5.6 reasoning to low, medium or high.
- **No classification for a named workflow.** A request that names its workflow
  starts it without a model call to classify the task (ADR 0079).

### Fixes

- **Official development installations** install and upgrade to the end. Preflight
  no longer requires the frontend image before it is built, and a release upgrade
  no longer waits for its own recovery journal.
- **Confirmation dialogs** grow to fit a long confirm label.

### Upgrading

`./flow-steward release upgrade --confirm` applies this release's database
migrations:
- role permissions;
- agent expiry reminders;
- the authenticator policy;
- connection poll delivery.

It takes the backup and maintenance window first, as in earlier releases. After the
upgrade, open *Settings → Email* and check that the system email sender is the one
you expect.
